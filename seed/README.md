# 시드 데이터

k6 측정에 쓸 게시판 데이터를 만든다. **세 사람이 각자 만들어도 완전히 같은 데이터가 나온다.**

측정은 "같은 조건에서 baseline 대비 배율"로 비교하므로, 데이터가 다르면 비교 자체가 무의미하다.
그래서 데이터 파일을 주고받는 대신 **생성 방법을 공유하고, 같은 결과임을 해시로 증명한다.**

읽을 문서는 이 파일 하나다. (Claude Code로 작업한다면 `.claude/skills/seed-data/SKILL.md`가 짝이다.)

---

## 쓰는 법

```bash
cp .env.example .env          # 레포 루트. JWT_SECRET만 팀 값으로 채운다
bash seed/seed.sh init        # S 생성 + 검증 (약 30초)
```

그다음부터는 필요한 규모로 갈아끼운다.

```bash
bash seed/seed.sh s|m|l       # 없으면 만들고, 있으면 bench만 교체(수십 초)
bash seed/seed.sh status      # 지금 뭐가 붙어 있는지
```

Docker Desktop만 있으면 된다. PostgreSQL은 설치하지 않는다.
앱은 `.env`의 `DB_WRITE_URL`이 가리키는 **`bench`** 에 붙는다. 프로파일을 바꿔도 이름은 `bench`로
고정이라 앱 설정을 손댈 일이 없다.

## 설계 결정 네 가지

리뷰에서 봐주셨으면 하는 부분이다.

### 1. 데이터가 아니라 생성기를 공유한다

맥과 윈도우가 섞여 있어 PGDATA 물리 백업을 쓸 수 없다(CPU 아키텍처에 묶인다).
덤프는 이식성은 좋지만 L 기준 1.5~3GB를 주고받아야 하고, 파라미터를 하나 바꿀 때마다
다시 만들어 다시 배포해야 한다. 생성 스크립트는 몇 KB다. `pgbench`나 TPC-H가 쓰는 방식이다.

성립 조건은 **결정성**이다. `random()`과 `setseed()`를 쓰지 않고 모든 값을 행 id의 md5에서
파생한다. 타임스탬프는 `seed_meta.epoch` 기준 상대 초로 fingerprint를 계산해서, 빌드 시각이
사람마다 달라도 같은 값이 나온다. 실제로 지웠다 다시 만들어 확인했다.

### 2. 규모는 절대 숫자가 아니라 DB 메모리에서 역산한다

```
posts 1개당 크기 = (1.17KB + 본문크기) × 1.52     # M 실측 2,350바이트
N(posts) = 목표크기 ÷ posts 1개당 크기
M = DB메모리 × 0.6 (캐시 안)      L = DB메모리 × 3~5 (캐시를 넘김)
```

나머지는 N에서 파생한다. `comments=3N`(그중 20%가 대댓글), `view_events=6N`, `likes=N`,
`users=N/10 + k6풀`, `post_stats=N`(1:1), `boards=20`.

**DB 메모리 값 하나만 정하면 M과 L이 자동으로 따라온다.** 2주차 표의 절대 숫자를 쓰지 않은
이유는, DB 컨테이너를 2GB로 잡으면 그 표의 M(6~8GB)이 이미 캐시를 3~4배 넘어
"M은 캐시 안"이라는 정의와 모순되기 때문이다. → 팀 확인 필요

**예외 하나.** 최근 24시간 창의 이벤트 수는 M과 L이 **같아야** 한다. 그래야 trending에서
"집계 대상은 같은데 테이블이 커서 느려진다"는 Volume 토픽의 질문이 분리된다.

### 3. 분포는 Zipf여야 한다

조회·좋아요·댓글을 균등분포로 깔면 핫 로우 경합도, 캐시 효과도, popular 정렬도 재현되지 않아
**튜닝 실험 자체가 성립하지 않는다.**

Zipf 역함수를 직접 계산한다. 빈도가 `r^-s`에 비례하고, `s=1`이면 `r = N^u`로 밀도가 정확히
`1/r`이 된다(설계서 v3의 `s: 1.0`). 처음에는 `floor(N × u^e)` 거듭제곱 근사를 썼는데
**1등이 너무 뾰족했다.** `e=8`, N=54만에서 난수의 18.8%가 통째로 1등으로 몰려 한 글에
댓글이 31만 개 붙었다. 진짜 Zipf로 바꾸니 1.9만 개로 내려왔다.

댓글만 `COMMENT_ZIPF_S=0.8`로 완화한다. `s=1`이어도 한 글에 10만 개가 붙어 상세조회 측정을
그 글 하나가 지배한다. 조회·좋아요는 핫 로우 경합이 목적이라 `s=1.0`을 쓴다.

### 4. 낡은 데이터로 측정하는 것을 막는다

템플릿이 최신인지는 **입력 해시**로 판단한다. 프로파일 값만 보면 안 된다. 앱 스키마가 바뀌었는데
"이미 최신"이라며 건너뛰면 **낡은 스키마로 만든 데이터로 측정하게 되고, 에러가 안 나서 아무도
모른다.** 실제로 한 번 당했다.

해시에 넣는 것은 프로파일 파생값, `sql/*.sql`, **앱 마이그레이션**, PostgreSQL 이미지 태그다.
`verify/*.sql`과 `seed.sh`와 `profiles/*.env` 원본은 **일부러 뺐다.** 해시가 바뀌면 템플릿을
다시 만들어야 하는데 L은 20분이 넘는다. 검증 문구를 고쳤다고 그 시간을 쓸 이유는 없다.

fingerprint 대조도 같은 목적이다. 기준값이 있고 입력 해시가 같은데 값이 다르면
**기준값을 덮어쓰지 않고 멈춘다.** 덮어쓰면 매번 자기 값이 기준이 되어 영원히 "일치"한다.
틀렸는데 맞다고 나오는 게 제일 나쁘다.

| 상황 | 동작 |
|---|---|
| 기준값 없음 | 내 값이 기준이 된다. 커밋하라고 알린다 |
| 입력 해시가 다름 | 값 비교를 하지 않는다. 기준값 갱신이 필요하다고 알린다 |
| 입력은 같은데 값이 다름 | 어디가 다른지 짚고 **덮어쓰지 않는다** |

## 앱·k6와의 계약

**앱.** 스키마는 시드가 **앱과 같은 마이그레이션 파일을 같은 버전 Flyway CLI(11.7.2)로** 적용한다.
그래서 앱이 떠도 재적용하지 않고 `ddl-auto=validate`도 통과한다. 앱이 요구하는 것은 전부
구현·검증돼 있다. 글마다 `post_stats` 1행, `setval`, `updated_at`을 `created_at`과 같게,
대댓글은 같은 글의 최상위 댓글만 깊이 1단계.

**k6 (유진과 확정 필요).** 둘 다 지키지 않으면 **에러 없이 조용히** 측정이 망가진다.

- **`event_id` 구간 분리** — 시드 UUID와 k6 UUID가 겹치면 k6의 신규 요청이
  `ON CONFLICT DO NOTHING`으로 무시되어 조회수가 안 오르고 사후 검증이 유실로 오판한다.
  시드는 UUID 앞 2자리를 `EVENT_NS`(기본 `00`)로 쓴다.
- **사용자 id 구간 분리** — `users`의 앞 구간(`1 .. N/10`)은 시드 활동 사용자,
  뒤 구간(`K6_USER_POOL`개, 기본 1만)은 **k6 전용 풀**이고 시드가 좋아요·댓글을 붙이지 않는다.
  안 나누면 k6의 좋아요가 기존 조합에 걸려 핫 로우 경합이 사라진다. FK 때문에 k6가 쓸 사용자도
  시드가 미리 만들어야 한다. **이 풀이 곧 JWT `sub` 목록이다.**
- **JWT는 시드가 발급하지 않는다.** k6가 `k6/crypto`로 런타임에 HS256 서명한다. 사전 발급은
  TTL 만료로 401이 나면 회차가 통째로 무효가 되고, 토큰 파일을 맥·윈도우 사이에 옮겨야 한다.

## 파일 구조

사람이 값을 바꾸는 곳은 **`profiles/`뿐**이다. 나머지는 절차다.

| 파일 | 역할 |
|---|---|
| `seed.sh` | 호스트에서 치는 유일한 명령. 규모 계산 → Postgres 기동 → SQL 실행 → 검증 → `bench` 교체 |
| `compose.seed.yml` | 시드 전용 Postgres + Flyway CLI. **측정용이 아니다**(측정용은 `bench-infra`) |
| `profiles/base.env` | 공통 노브. DB 메모리, 본문 길이, 크기 계수, 엔티티 비율, Zipf 지수, k6 풀 |
| `profiles/{s,m,l}.env` | 프로파일별 규모 목표 |
| `sql/00_helpers.sql` | 결정적 난수 함수, Zipf 역함수, 시각 기준점 |
| `sql/05_session.sql` | 적재용 설정(세션 `SET`). psql 호출이 나뉘면 세션도 나뉘므로 무거운 단계마다 넣는다 |
| `sql/10_prepare_load.sql` | FK·인덱스를 **카탈로그에서 정의를 떠서 보관하고 떼어낸다**(V1과 중복 관리 안 됨) |
| `sql/20~26_*.sql` | boards → users → posts → 최상위 댓글 → 대댓글 → likes → view_events |
| `sql/30_restore.sql` | FK·인덱스 복원. **FK 추가 시 전체 검사가 돌아 고아 행을 잡는다**(정합성 1차 관문) |
| `sql/40_post_stats.sql` | 카운터를 **원천 집계로** 채운다. 직접 넣으면 정합성 검증이 무의미해진다 |
| `sql/50_setval.sql` | 시퀀스 맞추기. 안 하면 `POST /posts`가 첫 요청부터 PK 충돌 |
| `sql/60_vacuum.sql` | `VACUUM ANALYZE`. 통계가 없으면 실행 계획이 엉망이 된다 |
| `sql/70_meta.sql` | `seed_meta` 표식 기록, 헬퍼 정리 |
| `verify/verify.sql` | 필수 검증 7개(실패 시 중단) + 분포·크기 리포트 |
| `verify/fingerprint.sql` | 테이블별 행 수 + 순서 무관 해시 합 |
| `fingerprints/*.txt` | 기준값. **git에 커밋한다** |

만들어지는 데이터베이스는 템플릿 `seed_s`/`seed_m`/`seed_l`(완성 후 **읽지도 쓰지도 않는다**)과
작업용 `bench`(매번 `FILE_COPY`로 복제)다. 시드가 쓸 DB는 시드가 직접 만들어서, 각자 compose가
만드는 DB 이름과 무관하다.

## 실측 (2026-09-19)

| 항목 | S | M | L |
|---|---|---|---|
| 생성 시간 | 30초 | 2분 23초 | **34분 21초** |
| 전체 크기 | 128MB | 1,231MB | 8,208MB |
| posts | 50,000 | 548,293 | 3,655,291 |
| users (시드 + k6풀) | 15,000 | 58,293 | 375,529 |
| comments (최상위 + 대댓글) | 150,000 (120,000 + 30,000) | 1,644,879 (1,315,903 + 328,976) | 10,965,873 (8,772,698 + 2,193,175) |
| post_likes | 50,000 | 548,293 | 3,655,291 |
| post_view_events | 300,000 | 3,289,758 | 21,931,746 |
| 최근 24시간 창 | 49,782 (목표 5만) | 999,773 (목표 100만) | 1,000,178 (목표 100만) |
| 상위 1% 조회 점유율 | 57.5% | 65.2% | 69.6% |
| 최다 댓글 | 2,912 | 18,953 | 84,043 |
| posts 1개당 크기 | 2,684바이트 | 2,348바이트 | 2,355바이트 |
| 필수 검증 | 7/7 | 7/7 | 7/7 |
| 앱 기동 | 9.6초 | 9.1초 | 9초대 |
| bench 교체(FILE_COPY) | 수 초 | 약 50초 | 3~6분 |

**크기 계수는 M 실측(2,350)을 쓴다.** M 2,348, L 2,355로 0.3% 차이라 **선형이 확인됐다.**
S만 2,684로 14% 큰데, 작은 테이블일수록 페이지 헤더와 덜 채워진 페이지의 상대 비용이 커서다.
S는 `POSTS_OVERRIDE`를 쓰므로 이 계수의 영향을 받지 않는다.

상위 1% 점유율이 규모에 따라 변하는 것은 `s=1` Zipf의 성질이다(`1 - ln(100)/ln(N)`).
세 규모 모두 이론값과 일치한다.

**24시간 창이 M과 L에서 거의 같다**(999,773 / 1,000,178). 테이블 크기만 6.7배 차이나므로,
trending 측정에서 "집계 대상은 같은데 테이블이 커서 느려진다"를 분리해 볼 수 있다.

**L은 34분이 걸린다.** 시작 전에 알고 있어야 한다. M(1.2GB, 2분 23초)의 6.7배 크기인데
시간은 14배다. 인덱스 구축과 집계가 규모에 대해 선형보다 느리게 증가한다.

## 알려진 한계

- **trending 24시간 창이 시간이 지나면 빈다.** 앱 쿼리는 `now() - 24h`인데 시드는 빌드 시점
  기준이다. 템플릿을 며칠 쓰면 창에 아무것도 안 남는다. `seed_meta.epoch`를 기록해 뒀으니
  복제 직후 최근 구간만 밀어주면 되지만 **아직 구현하지 않았다.**
- Flyway 11.7.2가 PostgreSQL 18을 공식 지원하지 않는다(경고만, 동작함). 팀 확인 필요.
- 규모 정의(절대 숫자 vs DB 메모리 역산)와 공유 방식(덤프 vs 생성기), 토큰 발급 시점은
  팀에서 확정이 필요하다.

## 부록: 환경별 함정

구현하면서 실제로 밟은 것들이다. 다시 밟지 않도록 남긴다.

- **PostgreSQL 18 이미지는 볼륨 경로가 바뀌었다.** `/var/lib/postgresql/data`가 아니라
  `/var/lib/postgresql`에 마운트한다. 전자면 "unused mount/volume"으로 기동 실패.
- **Git Bash(Windows)가 컨테이너 경로를 윈도우 경로로 바꾼다.** `MSYS_NO_PATHCONV=1`을 붙인다.
- **`DROP DATABASE`는 트랜잭션 블록 안에서 못 돈다.** `psql -c "a; b"`가 아니라 `-c "a" -c "b"`.
- **macOS 기본 bash는 3.2다.** `${var^^}`와 `md5sum`(맥은 `md5`)을 쓰면 맥에서 실패한다.
- **접속 세션이 하나라도 있으면 DB 복제·삭제가 실패한다.** 스프링 앱뿐 아니라
  **DataGrip 같은 GUI 클라이언트도 세션으로 잡힌다.** 프로파일 전환 전에 연결을 끊는다.
- **윈도우에서 clone하면 `.sh`가 CRLF가 되어 컨테이너 bash가 죽는다.** `.gitattributes`로
  LF를 고정했다. `src`의 마이그레이션 `.sql`은 Flyway 체크섬에 영향을 주므로 제외했다.
