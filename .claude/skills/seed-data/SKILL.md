# 시드 데이터

k6 측정용 데이터를 만들고, 규모(S/M/L)를 갈아끼운다.

**읽을 문서는 둘뿐이다.** 사람용 설명과 설계 근거, 파일별 역할, 환경 함정, 실측값은
전부 **`seed/README.md`**에 있다. 이 파일은 Claude가 실행할 때 필요한 절차와 판단 기준만 담는다.
같은 사실을 두 곳에 쓰지 마라. 막히면 먼저 `seed/README.md`를 읽어라.

**이 스킬은 절차만 안내한다. 실제 생성 로직은 `seed/` 아래 파일에 있다.**
대화 중에 즉석으로 SQL을 지어내 실행하지 마라. 세 사람이 같은 데이터를 가져야 하고,
그 보장은 파일에 고정된 SQL에서만 나온다. `seed/`에 없는 동작이 필요하면
먼저 파일로 만들고 그다음 실행한다.

Claude Code 없이도 같은 일이 되어야 한다. 모든 단계는 아래 한 줄로 실행된다.

```
bash seed/seed.sh <init|s|m|l|status>
```

호스트 셸은 이 한 줄만 쓰고, 실제 작업은 전부 컨테이너 안 psql과 Flyway CLI가 한다.

## 사용법

- `/seed-data` — 현재 상태 보고 (`seed.sh status`). 어떤 템플릿이 있고, `bench`에 지금 뭐가
  붙어 있고, fingerprint가 기준값과 맞는지.
- `/seed-data init` — **S만** 만든다. 환경 점검 → S 생성 → 검증 → fingerprint 대조.
  목적은 데이터 준비가 아니라 **이 환경에서 파이프라인이 도는지 1분 만에 확인하는 것**이다.
  M이나 L을 만들지 마라.
- `/seed-data S|M|L` — 그 프로파일을 쓸 수 있는 상태로 만든다.
  템플릿이 있으면 `bench`만 갈아끼우고(수십 초), 없으면 만들고 나서 갈아끼운다.
  이미 그 프로파일이 붙어 있으면 아무것도 하지 않는다.

L은 한 시간이 넘고 디스크를 많이 쓴다. 사람에게 확인받고 백그라운드로 돌린다.

## 실행 후 보고 형식

스크립트 출력을 그대로 흘리지 마라. **무엇이 어떻게 바뀌었는지**를 사람이 한눈에 보게 정리한다.
특히 오래 걸리는 작업(M 2분대, L 30분대)은 사람이 결과만 보고 판단할 수 있어야 한다.

```
bench : M → L

  ✓ 템플릿 seed_l 생성        posts 3,655,291 / 8,216MB / 32분 14초
  ✓ 필수 검증                 7/7 통과
  ✓ 24시간 창                 999,841건 (목표 1,000,000)
  ✓ 상위 1% 조회 점유율        66.1%
  ! fingerprint               기준값 없음 → 이 값이 기준이 된다

  다음: seed/fingerprints/l.txt 를 커밋하세요.
        앱을 띄우면 L 규모 데이터를 봅니다. .env는 그대로 둡니다.
```

원칙 네 가지다.

1. **전/후를 먼저 말한다.** `bench`에 무엇이 붙어 있었고 지금 무엇이 붙었는지.
   바뀐 게 없으면 "이미 L이 붙어 있어 아무것도 하지 않았다"고 분명히 말한다.
2. **확인한 것을 항목으로 보여준다.** 통과는 `✓`, 사람이 조치해야 하면 `!`.
   검증 7/7을 그냥 "통과"로 넘기지 말고 실제 수치를 붙인다. 목표값과 나란히 둔다.
3. **다음에 할 일을 말한다.** fingerprint 커밋, 앱 재기동, 팀에 알릴 것 등.
4. **예상과 다른 값은 반드시 짚는다.** 크기가 목표에서 10% 넘게 벗어났거나,
   상위 1% 점유율이 이론값과 다르거나, 생성 시간이 기준값의 2배를 넘으면
   통과했더라도 "이건 확인이 필요하다"고 말한다.

실패했을 때도 같다. 어느 단계에서 왜 멈췄고 무엇을 하면 되는지를 앞에 두고,
스택트레이스나 SQL 오류 원문은 그다음에 붙인다.

## 정상 실행 출력

이미 최신인 경우다. 생성이 필요하면 [1/6]~[6/6] 단계가 사이에 찍힌다.

```
프로파일 M — posts 548,293  (DB 메모리 2GB x 0.6 = 1.2GB 목표)
  users 58,293 (시드 48,293 + k6풀 10,000)
  comments 1,644,879 (최상위 1,315,903 + 대댓글 328,976)
  view_events 3,289,758   likes 548,293
  24시간 창 1,000,000건   이벤트 분포 3.2898일   입력 해시 e479f6f10d3d

  템플릿 seed_m 이미 최신 — 생성 건너뜀
  fingerprint 기준값과 일치

  bench : S → M
  [완료] M 준비됨 (49초)
```

## 스키마는 Flyway가 만든다

앱과 **같은 마이그레이션 파일**을 **같은 버전 Flyway CLI**(11.7.2)로 적용한다.
`flyway_schema_history`를 Flyway가 직접 정확한 체크섬으로 채우므로, 나중에 앱이 떠도
재적용을 시도하지 않는다. 스키마 정의를 시드 쪽에 복제하지 마라.

적재 속도를 위해 FK와 조회용 인덱스는 **카탈로그에서 정의를 떠서 보관했다가 떼고,
적재 후 되돌린다**(`10_prepare_load.sql` / `30_restore.sql`). V1·V2 파일과 중복 관리되지 않는다.

## 데이터베이스 이름 계약

사람마다 compose가 만드는 DB 이름이 다르다. 그래서 **시드가 쓸 DB는 시드가 직접 만든다.**
관리용 DB(`postgres`)에 접속해서 아래 넷을 만들고, 사람이 이미 쓰던 DB는 건드리지 않는다.

- `seed_s`, `seed_m`, `seed_l` — 템플릿. 완성 후 **읽지도 쓰지도 않는다.**
  접속 세션이 하나라도 있으면 복제가 실패한다.
- `bench` — 작업용. 앱과 k6가 붙는 곳. 매번 템플릿에서 복제해 만든다.

접속 정보(host/port/user/password)만 `.env`로 각자 환경에 맞춘다.
앱은 `DB_WRITE_URL`이 `bench`를 가리키게 한다.

## 원칙

1. 데이터는 **PostgreSQL 안에서 SQL로** 만든다(`generate_series` + `INSERT ... SELECT`).
   앱이나 JPA로 넣지 않는다.
2. 모든 값은 **행 id의 해시에서 파생**한다. `random()`과 `setseed()`는 금지다.
   `setseed()`는 단일 세션 순차 실행에서만 재현되고 병렬 쿼리가 끼면 깨진다.
3. **조회, 좋아요, 댓글**은 Zipf로 치우치게 만든다(`_seed.zipf`, 역함수 직접 계산). 균등분포는 금지다.
   댓글만 `COMMENT_ZIPF_S`로 완화한다. `s=1`이면 한 글에 댓글이 10만 개 붙어 측정을 지배한다.
   균등하면 핫 로우 경합도, 캐시 효과도, popular 정렬도 재현되지 않아 튜닝 실험이 성립하지 않는다.
4. 규모 값은 `seed/profiles/`에서만 읽는다. SQL에 숫자를 하드코딩하지 않는다.
5. 적재용 설정(`maintenance_work_mem`, `synchronous_commit`, `work_mem`)은
   **세션 단위 `SET`**으로 건다. 서버 설정을 바꾸지 마라. 측정용 설정에 섞이면 결과가 무효다.
6. `post_stats`는 직접 넣지 말고 **원천 테이블 집계로** 채운다. 정합성 검증 대상이기 때문이다.
7. 시드가 만드는 `event_id`와 k6가 측정 중 만드는 `event_id`는 **구간을 나눈다.**
   겹치면 k6의 신규 요청이 `ON CONFLICT`로 조용히 무시되어 조회수가 안 오르고,
   사후 검증이 유실로 오판한다.
8. **JWT를 발급하지 않는다.** 토큰은 k6가 `k6/crypto`로 런타임에 HS256 서명한다.
   시드의 책임은 `users` 행 생성과 `JWT_SECRET` 공유까지다.

## 규모 계산

절대 숫자를 쓰지 않는다. **DB 컨테이너 메모리에서 역산한다.**

```
posts 1개당 크기 ≈ (1.17KB + 본문크기) × 1.52
N(posts) = 목표크기 ÷ posts 1개당 크기
목표크기: M = DB메모리 × M_TARGET_RATIO, L = DB메모리 × L_TARGET_RATIO
```

나머지 테이블은 N에서 파생한다.
`comments = 3N`, `post_view_events = 6N`, `post_likes = N`, `users = N/10`,
`post_stats = N`(1:1 강제), `boards = 20`(고정).

**예외: 최근 24시간 창의 이벤트 수는 절대값으로 고정한다.**
M과 L이 같은 창 크기를 가져야 "집계 대상은 같은데 테이블이 커서 느려진다"는
Volume 토픽의 질문이 분리된다. 이벤트 분포 기간은 `전체 이벤트 ÷ 24시간 창`으로 따라온다.
`N`이 작아 전체 이벤트가 창보다 적어지면 창 값에 상한을 건다.

`BYTES_PER_UNIT`은 추정값이다. S를 만든 뒤 `pg_total_relation_size`로 실측해
프로파일 파일을 갱신하고, 그 계수로 M과 L을 다시 뽑는다.

## 파일 구성

`seed.sh`가 아래를 번호 순서대로 실행한다. 각 파일의 자세한 역할은 `seed/README.md` 2절에 있다.

```
seed.sh                     호스트 진입점. 규모 계산 → Postgres 기동 → 아래 실행 → bench 교체
compose.seed.yml            시드 전용 Postgres + Flyway CLI (측정용 아님)
profiles/base.env           사람이 만지는 값. 나머지는 절차다
profiles/{s,m,l}.env        프로파일별 규모 목표
sql/00_helpers.sql          결정적 난수 함수, 시각 기준점
sql/05_session.sql          적재용 설정 (세션 SET. 무거운 단계마다 다시 넣는다)
sql/10_prepare_load.sql     FK·인덱스 떼기(정의는 카탈로그에서 보관), autovacuum off
sql/20~26_*.sql             boards → users → posts → comments_top → comments_replies
                            → post_likes → view_events
sql/30_restore.sql          FK·인덱스 복원(고아 행이 있으면 여기서 실패), autovacuum 원복
sql/40_post_stats.sql       카운터를 원천 집계로 채움
sql/50_setval.sql           시퀀스 맞추기
sql/60_vacuum.sql           VACUUM ANALYZE
sql/70_meta.sql             seed_meta 기록, 헬퍼 정리
verify/verify.sql           필수 검증 7개 + 분포·크기 리포트
verify/fingerprint.sql      행 수 + 순서 무관 해시 합
fingerprints/*.txt          기준값. git에 커밋한다
```

## 실행 절차

1. 적재용 설정을 세션에 `SET`한다. DB TimeZone이 UTC인지 확인한다.
2. Flyway로 스키마를 만든 뒤 FK와 조회 인덱스를 **떼어 둔다**(정의는 카탈로그에서 보관).
   PK와 UNIQUE는 남긴다. UNIQUE는 중복 생성을 잡아주는 그물이다.
3. 부모에서 자식 순서로 적재한다:
   boards → users → posts → **최상위 댓글 → 대댓글** → post_likes → post_view_events.
   대댓글은 부모 댓글을 먼저 고르고 `post_id`를 물려받아 "같은 글" 규칙을 구조적으로 보장한다.
4. 보조 인덱스와 FK를 만든다.
5. `post_stats`를 원천 집계로 채운다.
6. `setval`로 시퀀스를 최대 id 다음으로 민다. 안 하면 `POST /posts`가 첫 요청부터 PK 충돌이 난다.
7. `VACUUM ANALYZE`. 안 하면 실행 계획이 엉망이 되어 측정이 무의미해진다.
8. 아래 검증을 전부 통과시킨다.
9. `seed_meta`를 기록하고 fingerprint를 남긴다.
10. 템플릿으로 굳히고 `bench`를 복제한다.

```sql
DROP DATABASE IF EXISTS bench;
CREATE DATABASE bench TEMPLATE seed_m STRATEGY FILE_COPY;
```

`FILE_COPY`를 반드시 명시한다. PG15+ 기본값 `WAL_LOG`는 복사량만큼 WAL을 써서 큰 DB에서 매우 느리다.

## 낡음 판정과 fingerprint 대조

**템플릿이 최신인지는 `inputs_hash`로 판단한다.** 프로파일 값만 보면 안 된다.
생성 SQL이나 앱 스키마가 바뀌어도 "최신"이라고 건너뛰어 **낡은 데이터로 측정하게 된다.**
에러가 나지 않아 아무도 모른다. 실제로 한 번 당했다.

해시에 넣는 것은 프로파일 파생값, `sql/*.sql`, 앱 마이그레이션, PostgreSQL 이미지 태그다.
`verify/*.sql`과 `seed.sh`와 `profiles/*.env` 원본은 **일부러 뺀다.**
해시가 바뀌면 L을 한 시간 다시 만들어야 하므로, 데이터를 바꾸지 않는 것은 넣지 않는다.

**fingerprint는 덮어쓰지 마라.** 기준값이 있고 입력 해시가 같은데 값이 다르면
그 파일을 건드리지 않고 무엇이 다른지 보고한다. 덮어쓰면 "누가 기준인지"가 사라져
매번 자기 값이 기준이 되고 영원히 "일치"한다.

입력 해시가 다르면 값 비교 자체를 하지 마라. 다른 입력으로 만든 데이터라 다른 게 당연하고,
"내 환경이 이상한가"와 "기준값이 낡았나"를 구분해 줘야 한다.

## seed_meta

시드와 함께 넣는 작은 표식 테이블이다. 템플릿을 복제하면 같이 복사되므로,
`bench`에 붙어 이것만 읽으면 **지금 어느 프로파일이 붙어 있는지** 알 수 있다.

```
seed_meta(profile, inputs_hash, epoch, built_at, pg_version, params)
```

- `inputs_hash`가 달라지면 템플릿이 낡았다고 알려준다. 무엇이 해시에 들어가는지는 위 절 참고.
- `epoch`는 모든 타임스탬프의 기준점이다. fingerprint를 이 값 기준 상대 초로 계산해서,
  빌드 시각이 사람마다 달라도 같은 값이 나온다.
- 측정 시작 전에 `bench`의 프로파일이 시나리오가 요구하는 것과 맞는지 확인할 수 있다.

## 검증 (전부 통과해야 완료 — 현재 필수 7개)

- 테이블별 행 수가 프로파일 계산값과 정확히 일치
- `post_stats`가 원천 집계와 100% 일치 (불일치 0건)
- 시퀀스가 최대 id보다 큼
- autovacuum이 모든 테이블에서 원복됨
- `event_id` 네임스페이스가 전부 `EVENT_NS`
- **대댓글 규칙**: 부모가 대댓글이거나 다른 글의 댓글인 행 0건, 대댓글 수 일치
- **`updated_at` = `created_at`** (비워 두면 `now()`라 빌드 시각마다 달라진다)

FK 정합성은 `30_restore.sql`이 FK를 되돌릴 때 전체 검사로 걸러진다.
분포(상위 1% 점유율), 24시간 창 크기, 실제 테이블 크기는 **경고만** 낸다. 조정 대상이지 실패가 아니다.

## fingerprint

테이블마다 `count(*)`와 **행별 md5 해시의 합**을 낸다(`verify/fingerprint.sql`).
행 순서는 사람마다 다를 수 있으므로 **순서에 무관한 합**을 쓴다.
`timestamptz`는 `seed_meta.epoch` 기준 **상대 초**로 정규화한다. 그래야 빌드 시각이 달라도
같은 값이 나온다. DB TimeZone은 UTC로 고정한다.
`updated_at`은 항상 `created_at`과 같으므로 해시에 넣지 않고 검증에서만 확인한다.

결과를 `seed/fingerprints/<profile>.txt`에 쓴다. **이 파일은 git에 커밋한다.**
- 레포에 기준값이 없으면 지금 만든 값이 기준이 된다. 커밋할지 사람에게 묻는다.
- 기준값이 있으면 자동으로 대조하고 판정한다. 사람이 값을 옮겨 적게 하지 마라.
- 어긋나면 원인을 좁혀서 제시한다.
  행 수부터 다르면 프로파일 값이 서로 다른 것이고,
  행 수는 같은데 해시만 다르면 DB TimeZone이나 PostgreSQL 메이저 버전을 의심한다.

## 실패했을 때

**무엇이 / 왜 / 어떻게** 세 가지를 같이 말한다. 단계 번호를 반드시 붙인다.

```
[적재 실패] 3/8 단계 posts 생성 중 중단
  원인: 디스크 공간 부족 (no space left on device)
  조치: 공간 확보 후 같은 명령을 다시 실행하세요. 완료된 단계는 건너뜁니다.
```

자주 나오는 것들:

- **Docker 엔진 연결 불가** → Docker Desktop이 실행 중이 아니다.
- **디스크 부족** → 필요량과 여유량을 숫자로 같이 보여준다. 데이터 크기의 2배가 필요하다
  (적재 중 인덱스 빌드 임시 공간과 WAL).
- **포트 점유** → 로컬 PostgreSQL이나 다른 컨테이너가 쓰고 있다. `.env`의 포트를 바꾼다.
- **`JWT_SECRET` 없음** → `.env`에 없다. 팀에서 받아 넣는다.
- **템플릿 복제 실패** → `bench`나 템플릿에 접속 세션이 있다. 보통 스프링 앱이 떠 있는 경우다.
  앱을 내리고 다시 시도한다. 강제로 끊을지 사람에게 묻는다.
- **검증 실패** → 어느 항목이 왜 틀렸는지와 고칠 파일을 짚는다.
  쏠림이 약하면 `ZIPF_S`(조회·좋아요)나 `COMMENT_ZIPF_S`(댓글)를 올린다.
- **크기 추정 어긋남** → 실패가 아니라 보정 기회다. `BYTES_PER_UNIT` 갱신을 제안한다.

재시도는 안전해야 한다. 이미 끝난 단계는 건너뛴다.

## 환경별 함정 (실제로 밟은 것들)

다시 밟지 마라. 2026-09-19 기준.

- **PostgreSQL 18 이미지의 볼륨 경로가 바뀌었다.** `/var/lib/postgresql/data`가 아니라
  `/var/lib/postgresql`에 마운트해야 한다. 전자로 하면 "unused mount/volume" 에러로 기동에 실패한다.
- **Git Bash(Windows)가 컨테이너 경로를 윈도우 경로로 바꿔버린다.** `-f /seed/sql/x.sql`이
  `C:/Program Files/Git/seed/sql/x.sql`이 되어 "No such file"이 난다.
  docker 명령 앞에 `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL="*"`를 붙인다(seed.sh가 이미 한다).
- **`DROP DATABASE`는 트랜잭션 블록 안에서 못 돈다.** `psql -c "a; b"`는 한 트랜잭션으로 묶이므로
  `-c "a" -c "b"`로 나눠 준다.
- **macOS 기본 bash는 3.2다.** `${var^^}` 같은 bash 4 문법과 `md5sum`(맥은 `md5`)을 쓰면
  맥에서 첫 줄부터 실패한다. 맥·윈도우 양쪽에서 도는 게 이 작업의 전제다.
- **psql 호출이 나뉘면 세션도 나뉜다.** 세션 `SET`으로 건 적재용 설정이 사라진다.
  무거운 작업(인덱스 재구축, VACUUM)을 하는 호출마다 `05_session.sql`을 함께 넣어야 한다.
- **템플릿이나 `bench`에 접속 세션이 하나라도 있으면 복제·삭제가 실패한다.**
  스프링 앱뿐 아니라 DataGrip 같은 GUI 클라이언트도 세션으로 잡힌다.
